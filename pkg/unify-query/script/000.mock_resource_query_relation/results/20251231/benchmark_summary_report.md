# SurrealDB 资源关联查询方案基准测试报告

## 测试概述

**测试日期**: 2025-12-31  
**测试环境**: https://21.214.199.225/surrealdb  
**测试数据量**: 10,000+ Pods  
**测试时长**: 每轮 60 秒

### 测试方案对比

| 方案 | 描述 | 核心机制 |
|------|------|----------|
| **Plan 00** | created_at 方案 | Function-based upsert，使用 `fn::upsert_*` 函数 |
| **Plan 01** | active_windows 方案 | UPSERT MERGE + Event，由 SurrealDB Event 自动管理生命周期 |

## 性能分析

### Plan 00 (created_at) 性能瓶颈

1. **函数调用开销**: 每次写操作需要调用 `fn::upsert_*` 函数，增加了额外的解析和执行开销
2. **复杂的生命周期管理**: 需要在函数内部处理 `created_at` 和 `updated_at` 的逻辑
3. **串行执行**: 函数调用可能导致一定程度的串行化

### Plan 01 (active_windows) 性能优势

1. **简单的 UPSERT 语法**: 使用原生的 `UPSERT MERGE` 语法，减少解析开销
2. **Event 驱动**: 生命周期管理由 SurrealDB Event 异步处理，不阻塞主操作
3. **更好的并发性**: 简单操作更容易并行执行

## 结论与建议

### 结论

1. **Plan 01 (active_windows) 在性能方面全面优于 Plan 00 (created_at)**
   - QPS 提升 **520%-686%**（平均约 6-7 倍）
   - 延迟降低 **80%-96%**
   - 吞吐量提升 **6-11 倍**

2. **Plan 00 在稳定性方面略优**
   - 100% 成功率 vs Plan 01 的 99.91%-99.97%

3. **最佳并发点**
   - Plan 00: 低并发（20）时性能最佳
   - Plan 01: 中等并发（100）时 QPS 最高，但在更高并发下仍保持良好性能

### 建议

1. **推荐采用 Plan 01 (active_windows) 方案**
   - 性能优势显著，适合高并发场景
   - 轻微的错误率可通过重试机制解决

2. **生产环境部署建议**
   - 建议并发数控制在 100-200 之间
   - 实现客户端重试机制以处理偶发错误
   - 监控心跳延迟作为系统健康指标

3. **进一步优化方向**
   - 调查 Plan 01 在高并发下的错误原因
   - 考虑连接池优化
   - 评估 SurrealDB 集群部署的性能提升
