## 一、测试背景与目的

### 1.1 测试背景

本次测试旨在评估 SurrealDB 作为资源关联查询存储后端的性能表现。SurrealDB 是一款多模型数据库，支持图查询、关系查询等多种数据模型，适合存储 Kubernetes 资源之间的关联关系（如 Pod-Service 关系）。

### 1.2 测试目的

1. 评估 SurrealDB 在不同并发负载下的吞吐量（QPS）
2. 测量不同读写比例场景下的延迟表现
3. 验证高并发场景下的稳定性和健康状态
4. 为生产环境部署提供参数配置建议

## 三、测试方法

### 3.1 测试架构

```
┌─────────────────────────────────────────────────────────────┐
│                    Benchmark Client                          │

│  │ (N threads) │  │   Thread    │  │                     │  │
│  └──────┬──────┘  └──────┬──────┘  └──────────┬──────────┘  │
│         │                │                     │             │
└─────────┼────────────────┼─────────────────────┼─────────────┘
          │                │                     │
          ▼                ▼                     ▼
    ┌─────────────────────────────────────────────────────────┐

    │  ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────────┐ │
    │  │   pod   │  │ service │  │pod_with_│  │ fn::upsert_*│ │

    │  └─────────┘  └─────────┘  └─────────┘  └─────────────┘ │
    └─────────────────────────────────────────────────────────┘
```

### 3.2 操作类型

| 操作类型 | 说明 | SQL 示例 |
|----------|------|----------|
| **read_single** | 单条记录读取 | `SELECT * FROM pod WHERE id = $id` |
| **read_batch** | 批量记录读取 | `SELECT * FROM pod WHERE namespace = $ns LIMIT 100` |
| **read_relation** | 关系查询 | `SELECT ->pod_with_service->service FROM pod WHERE id = $id` |
| **write_heartbeat** | 心跳更新（已存在记录） | `fn::upsert_pod({...}, $now, $tolerance)` |
| **write_new** | 新增记录 | `fn::upsert_pod({...}, $now, $tolerance)` |

### 3.3 测试参数

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `--concurrency` | 并发 Worker 数量 | 20 |
| `--duration` | 测试持续时间（秒） | 60 |
| `--read-ratio` | 读操作占比 (0-100) | 70 |
| `--heartbeat-ratio` | 写操作中心跳占比 (0-100) | 80 |
| `--health-interval` | 健康检查间隔（秒） | 5 |

### 3.4 测试场景

本次测试覆盖三种读写比例场景：

| 场景 | 读:写比例 | 说明 |
|------|-----------|------|
| **读多写少** | 70:30 | 典型查询场景，适合大部分监控查询需求 |
| **均衡负载** | 50:50 | 读写均衡场景，适合资源频繁变更的环境 |
| **写多读少** | 30:70 | 写入密集场景，适合大规模资源同步 |

每种场景测试以下并发级别：**20, 50, 100, 200, 300, 500** workers

## 五、结果分析

### 5.1 QPS 与读写比例关系

```
读写比例    20 Workers QPS    说明
────────────────────────────────────────────
70:30       ~30 QPS          读多写少，吞吐最高
50:50       ~26 QPS          均衡负载，吞吐中等
30:70       ~23 QPS          写多读少，吞吐最低
```

**结论**: 写操作比读操作更重，增加写比例会降低整体 QPS 约 15-25%。

### 5.2 延迟与并发关系

以 70:30 读写比例为例，p50 延迟随并发增长：

```
Workers    p50 延迟    相对 20 workers
────────────────────────────────────────
20         657ms       1.0x (基准)
50         1,629ms     2.5x
100        3,149ms     4.8x
200        6,626ms     10.1x
300        9,139ms     13.9x
500        15,902ms    24.2x
```

**结论**: 延迟与并发数呈近似线性关系，说明 SurrealDB 单实例存在明显的处理瓶颈。

### 5.3 稳定性分析

| 并发级别 | 健康检查表现 | 建议 |
|----------|--------------|------|
| ≤50 | 全部正常 | ✅ 推荐 |
| 100 | 偶发超时 (20-30%) | ⚠️ 谨慎使用 |
| 200+ | 频繁超时 (30-75%) | ❌ 不推荐 |

### 5.4 操作类型性能对比

在相同并发下，各操作类型延迟排序（从快到慢）：

1. **read_single** - 单条读取最快
2. **read_batch** - 批量读取略慢
3. **read_relation** - 关系查询中等
4. **write_heartbeat** - 心跳更新较慢
5. **write_new** - 新增记录最慢（涉及完整 upsert 逻辑）

---

## 六、性能瓶颈分析

### 6.1 主要瓶颈

1. **单实例处理能力上限**: 无论并发如何增加，QPS 稳定在 20-30，说明已达到单实例处理极限

2. **写操作开销大**: upsert 函数涉及：
   - 查询现有记录
   - 条件判断
   - 更新或创建操作
   - 索引维护

3. **连接竞争**: 高并发下 HTTP 连接复用不足，导致延迟线性增长

### 6.2 资源使用特征

- **CPU**: 写密集场景下 CPU 使用率更高
- **内存**: 随数据量增长，内存占用稳定
- **网络**: HTTP REST API 开销较大

---

## 七、建议与结论

### 7.1 生产环境配置建议

| 场景 | 建议并发数 | 预期 QPS | 预期 p50 延迟 | 适用场景 |
|------|-----------|----------|---------------|----------|
| 低延迟 | ≤20 | ~30 | <700ms | 实时查询、告警 |
| 一般 | 20-50 | ~28 | 1-2s | 常规监控 |
| 高吞吐 | 50-100 | ~25 | 2-4s | 批量同步 |
| **不推荐** | >200 | ~22 | >7s | - |

### 7.2 优化建议

1. **水平扩展**
   - 部署多个 SurrealDB 实例
   - 使用负载均衡分发请求

2. **读写分离**
   - 读操作走从库
   - 写操作走主库

3. **批量操作**
   - 合并多个写操作为事务
   - 减少网络往返次数

4. **连接池优化**
   - 使用持久连接
   - 配置合适的连接池大小

5. **缓存层**
   - 热点数据前置 Redis 缓存
   - 减少数据库直接访问

6. **索引优化**
   - 确保查询字段有合适索引
   - 定期分析慢查询

### 7.3 总结

| 指标 | 评价 |
|------|------|
| **吞吐量** | 单实例 ~30 QPS，适合中小规模场景 |
| **延迟** | 低并发下可接受 (<1s)，高并发下显著增长 |
| **稳定性** | 100% 成功率，但高并发下健康检查超时 |
| **扩展性** | 需要水平扩展支持大规模场景 |

**最终建议**: SurrealDB 适合作为资源关联查询的存储后端，但在高并发场景下需要：
- 控制并发在 50 以内
- 或部署多实例集群
- 配合缓存层使用
